# Проверочный проект B: рабочий экран SaaS

Используйте отдельный проект, не продолжение лендинга. Скопируйте [workflow-runs.json](fixtures/workflow-runs.json) как демо-данные. Это небольшой fixture для сценариев, а не нагрузочный тест.

## Запрос агенту

```text
Сделай рабочий экран «Запуски автоматизаций» для вымышленного продукта
RelayOps. Пользователь — инженер: найти неудачный запуск, понять причину
и повторить его. Нужны поиск по названию/ID, фильтр статуса, сортировка
по времени, таблица с пагинацией по 3 записи и панель деталей с логом.
Используй приложенный workflow-runs.json, явно обозначь демо-данные.

Дай возможность повторить failed-запуск. Во время запроса не допускай
дубликатов. Mock должен уметь показать медленный ответ, отказ и успех;
успех создаёт новый queued-запуск с новым ID, сохраняя исходный.
Для массового повтора выделяются только failed-запуски. Выбор сохраняется
между страницами одного фильтра, но сбрасывается при смене поиска/фильтра.
Проверь частичный отказ массовой операции.

Сохраняй фильтры, страницу и полезный контекст при открытии деталей
и возврате назад. На телефоне детали могут стать отдельным представлением.
Нужны начальная загрузка, пустой workspace, отсутствие результатов поиска,
ошибка с retry и read-only режим. Локальный mock, никаких реальных запусков.

Стиль: точный и компактный светлый интерфейс для разработчиков, холодные
нейтральные поверхности, табличные числа, ясные статусы, минимум декора.
Не добавляй маркетинговый hero, FAQ и произвольные KPI-карточки.
Используй существующий стек. Проверь основной сценарий, клавиатуру,
мобильный вид и восстановление после ошибок. Сообщи о границах проверки.
```

## Ручной прогон

1. Найти `run-1042`, открыть детали, прочитать причину сбоя и вернуться к прежним фильтрам/странице.
2. Повторить запуск с медленным ответом; двойной клик создаёт только одну новую запись.
3. Смоделировать отказ, сохранить контекст, повторить успешно: появляется новый ID со статусом queued; старый failed не переписывается.
4. Сравнить пустой workspace с пустым поиском. Во втором случае есть сброс фильтра, а исходные данные не исчезают.
5. Выделить failed-запуски на разных страницах; проверить количество и частичную ошибку. Повторная попытка затрагивает только неудачные элементы.
6. Сменить фильтр: выделение сбрасывается с понятной обратной связью. Удалить последнюю запись страницы в mock и проверить корректную страницу.
7. Переключить read-only: данные доступны, повтор недоступен с объяснением; mock также отклоняет действие.
8. Проверить сортировку/выделение клавиатурой, возврат фокуса из деталей, длинное название, null-duration, размеры экрана и отсутствие переполнения страницы.
9. Открыть ссылку на детали напрямую в новой вкладке и после перезагрузки. «К списку» возвращает в список с доступными фильтрами, даже если предыдущего экрана списка нет в истории; обычный переход список → детали → browser back также сохраняет контекст.

Сохранить снимки и результаты. Проверки mock не доказывают безопасность реального API или работу production-интеграции.
